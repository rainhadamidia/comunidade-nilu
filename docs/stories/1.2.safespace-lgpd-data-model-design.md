## Story

**As a** arquiteto/encarregado de dados do ILUMINNARE,
**I want** um documento de design do modelo de dados do SafeSpace que desacople o autor do conteúdo (pseudonimização real, não reidentificável), com base legal, política de retenção/expurgo e fluxo de apagamento formalmente propostos,
**so that** quando a persistência real do SafeSpace for implementada (Story 3, Lote 1b), ela suba sobre um modelo já revisado — sem criar passivo jurídico no exato commit que corrige o `FE-02`, e sem repetir o padrão de `personality_notes` (que expõe `user_id` diretamente, adequado para um "diário" não-sensível, mas **não** para desabafo de saúde emocional).

## Acceptance Criteria

1. Existe um documento `docs/prd/safespace-lgpd-data-model.md` descrevendo o modelo de dados proposto: tabelas envolvidas, colunas, e o mecanismo exato de desacoplamento autor↔conteúdo.
2. O design cobre explicitamente os 4 elementos exigidos pelo `GOV-L01` (assessment, linha 121): **base legal/consentimento**, **minimização**, **retenção/expurgo**, **direito ao apagamento**.
3. O documento demonstra, com um exemplo concreto de query, que um `SELECT` direto nas tabelas expostas ao client autenticado **não consegue** reidentificar o autor de um post (este é o "teste de reidentificação" citado como gate na suíte de testes do assessment — seção "E2E de negócio").
4. O design **não inclui migration SQL executável** — é proposta de design para revisão do `@architect` (quality gate desta story). A migration real é entregue na Story 3 (Lote 1b), depois que este design for aprovado.
5. A base legal proposta (qual hipótese da LGPD ampara o tratamento de dado sensível de saúde neste contexto B2B) é documentada como **recomendação técnica**, com nota explícita de que a decisão final precisa de validação jurídica (ação humana, fora do escopo de dev) antes da Story 3 poder subir em produção.
6. O documento confirma por escrito que **não há dados legados a migrar** — hoje o SafeSpace é 100% mock local (`src/pages/SafeSpace.tsx` usa `useState` com dados de `src/lib/mockData.ts`), então não existe nenhum desabafo real já persistido em risco.
7. O design propõe explicitamente o mecanismo de retenção/expurgo (quem/quando os dados de autoria são apagados) e o mecanismo de "direito ao apagamento" (como o próprio autor pode pedir a remoção do seu post).

## Dev Notes

### Contexto do Epic

Segunda metade da Story 1 do Epic 01. Bloqueia a Story 3 (Lote 1b — SafeSpace persistido de verdade), que só pode subir **sobre** este design pronto (ADR-08.2, `docs/prd/technical-debt-assessment.md` linha 146-154). [Source: docs/prd/technical-debt-assessment.md#adr-082]

### Por que o padrão `personality_notes` NÃO se aplica direto aqui

`docs/prd/technical-debt-assessment.md` recomenda "seguir o padrão `personality_notes`" para a **mecânica de migração** (sair de `useState` para tabela real, com RLS habilitada, índice, etc.) — mas **não** para o campo de autoria. A migration real (`supabase/migrations/20260704143449_personality_notes.sql`) faz isso:

```sql
CREATE TABLE public.personality_notes (
  id UUID ... PRIMARY KEY,
  user_id UUID NOT NULL REFERENCES auth.users(id) ON DELETE CASCADE,
  ...
);
CREATE POLICY "Users view own personality notes"
  ON public.personality_notes FOR SELECT
  USING (auth.uid() = user_id);
```

Isso expõe `user_id` como coluna comum, com policy que permite ao próprio usuário (e a admins) ver o vínculo autor↔conteúdo. **Correto para um relato de personalidade** (não é dado sensível de saúde), **incorreto para o SafeSpace** — um "desabafo anônimo" sobre saúde emocional com `user_id` visível/consultável é pseudonimização reidentificável, não anonimização real (exatamente o alerta do `GOV-L01`: "'Anônimo' client-side com `user_id` = pseudonimização (reidentificável), não anonimização"). [Source: docs/prd/technical-debt-assessment.md linha 121; supabase/migrations/20260704143449_personality_notes.sql]

### Infraestrutura já disponível para reaproveitar

- `public.has_role(_user_id uuid, _role app_role)` já existe (`supabase/migrations/20260421180824_*.sql`) — usar para restringir a RPC de leitura de autoria a admins/compliance.
- `app_role` enum já existe (`admin`, `moderator`, `user`) — não precisa criar novo enum de papel.
- Padrão de RLS + índice de `personality_notes` é a referência estrutural (não a de exposição de autoria).

### Estado atual do SafeSpace (confirmado, não é dívida inventada)

`src/pages/SafeSpace.tsx` usa `useState<SafeSpacePost[]>(initialPosts)` — todo post criado por `handlePost()` só existe em memória do componente, se perde ao dar refresh. `SafeSpacePost` (`src/lib/mockData.ts`) tem `id`, `content`, `timestamp`, `comments`, `likes` — nenhum campo de autor hoje. [Source: src/pages/SafeSpace.tsx linhas 9-39; src/lib/mockData.ts linhas 26-32]

### O que esta story NÃO faz (fora de escopo, não inventar)

- Não escreve a migration SQL de fato (Story 3).
- Não decide a base legal final nem o prazo de retenção exato — propõe, mas a decisão final é jurídica/de negócio (ação humana).
- Não mexe na UI do SafeSpace (Story 1.3).
- Não implementa a RPC de publicação (Story 3) — só desenha a assinatura/comportamento esperado dela.

### Testing

- Esta story não gera código executável, então não há testes automatizados dela mesma.
- Critério de "teste" aqui é uma revisão de design pelo `@architect` (quality gate): confirmar por leitura do documento que a query de exemplo (AC 3) realmente não reidentifica o autor com as permissões propostas.
- Quando a Story 3 implementar de fato, os testes reais de reidentificação (`get_advisors(security)`, teste de `select user_id via API`) citados no assessment (seção "Suíte de testes", item 4) devem passar contra o modelo aqui desenhado.
